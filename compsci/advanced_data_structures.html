14.1 Arrays

Write out student1, student2, student3... and keep going, and at some point it becomes obvious this doesn't scale. An array replaces all of them with one generalized container.

14.1.1 Why Generalizing Beats Repeating

An array holds many values under one name, each reachable by a numbered position called an index. Indexes start at 0, not 1 — the first element is array[0].

Breaking It Down: Arrays: One Name, Many Values

You met lists back in Chapter 10. An array is the same idea: one variable that holds many values in order, like a row of lockers under a single name. Each spot has a number, its index, and counting starts at 0. So in an array of 6 names, the first name is at index 0 and the last is at index 5.

Why bother? Look at the script below with six separate variables. To print all six names, you need six separate lines. To add a seventh student, you have to add a new variable and a new line. Every change means editing the code in several places, and it's easy to forget one.

With an array, you write the names once and use one loop to visit them all. The loop uses names.length, the number of items in the array, to know when to stop. That's what generalizing means: writing code that works for any number of items instead of exactly six. Add a seventh, or seventy, and the loop doesn't change at all.

Here's the pattern you'll use in the Array Refactor activity:

const names = ["Alex", "Brianna", "Carlos"];
for (let i = 0; i < names.length; i++) {
  Logger.log(names[i]);
}
// Add a name to the list, and the loop still works unchanged.
Worked Example: Refactoring Six Variables

Six separate variables, six separate lines every time you want to do something with all of them. One array plus one loop replaces every one of those lines — and unlike the six variables, the array works exactly the same whether you have 6 students or 600.

The trap: students often think arrays are just "a fancier way to store stuff." The real reason they matter is generalization — one loop over an array handles any number of items, while six hardcoded variables only ever handle exactly six.

The Script to Refactor
function showStudents() {
  var student1 = "Alex";
  var student2 = "Brianna";
  var student3 = "Carlos";
  var student4 = "Destiny";
  var student5 = "Ethan";
  var student6 = "Fatima";

  Logger.log(student1);
  Logger.log(student2);
  Logger.log(student3);
  Logger.log(student4);
  Logger.log(student5);
  Logger.log(student6);
}
Breaking It Down: Reading Spreadsheet Data into an Array

The last step of the Array Refactor asks you to read real cells from a Google Sheet into an array. You do that with getRange(...).getValues(). This is one of the most useful lines in Apps Script, but it has one surprise: it gives you an array of arrays, also called a 2D array.

Think of it like this: the outer array is a list of rows, and each row is its own little array of cells. So data[0] is the whole first row, and data[0][1] is the first row's second cell (column B). The first number picks the row, and the second number picks the column. Both start counting at 0.

To visit every row, loop through the outer array. Here's code that reads names from A2:A6 and logs each one:

const sheet = SpreadsheetApp.getActiveSheet();
const data = sheet.getRange("A2:A6").getValues();   // 5 rows, 1 column
for (let i = 0; i < data.length; i++) {
  Logger.log(data[i][0]);   // row i, column 0 (column A)
}

If your log shows things like [Alex] with square brackets around each name, you logged a whole row (data[i]) instead of the cell inside it (data[i][0]). That's the most common mistake with getValues(), and now you know the fix.

14.2 Linked Lists

Picture students standing in a numbered row — that's an array. Inserting someone new in the middle means everyone after them has to physically shift down one spot. Now picture each student instead holding a card naming who comes next — that's a linked list, and inserting someone new only means updating two cards.

Breaking It Down: How a Linked List Works

A linked list stores items in a chain. Each item is called a node, and every node holds two things: its value (like a name) and a pointer to the next node (often called next). The last node's next is null, which means "nothing comes after me."

Picture a scavenger hunt. Each clue tells you something, and also tells you where to find the next clue. You can't skip straight to clue #7. You have to follow the chain from the start. That's exactly how a linked list works, and it's why getting "item #7" is slower than with an array.

But inserting is easy. To add someone between Amara and Ben, you don't move anyone. You make a new node pointing to Ben, then change Amara's pointer to the new node. That's just two changes, whether the list has 4 people or 4 million. In Apps Script, each node can be a simple object:

const node3 = { value: "Chen",  next: null };
const node2 = { value: "Ben",   next: node3 };
const node1 = { value: "Amara", next: node2 };

// Insert "Bea" between Amara and Ben: only two changes
const newNode = { value: "Bea", next: node2 };
node1.next = newNode;

let current = node1;
while (current !== null) {
  Logger.log(current.value);   // Amara, Bea, Ben, Chen
  current = current.next;
}

The while loop follows the chain: start at the first node, log its value, then jump to current.next. When current becomes null, you've reached the end. This is the walk you'll write in the Structure Comparison activity.

14.2.1 Honest Tradeoffs, Not a "Better" Structure

OperationArrayLinked List
Access element by indexInstantMust walk from the start
Insert in the middleEverything after it shiftsCheap — no shifting
Delete from the middleEverything after it shiftsCheap — no shifting
Search for a value by contentMust check each elementMust check each element

That last row is deliberate — not every operation favors one structure. Searching for a value (not by index) is equally slow on both, because neither one can skip ahead without checking.

Breaking It Down: Reading the Tradeoff Table

Access by index means "give me item #14." An array can jump straight there, because it knows exactly where each numbered spot is, like going straight to locker #14. A linked list has to start at the first node and follow 13 pointers to get there.

Insert or delete in the middle is the opposite. In an array, everything after that spot has to shift over to make room or close the gap, like everyone in a numbered line taking one step. With 10,000 items, that could mean thousands of moves. In a linked list, you only update the pointers on the neighbors, so nobody else moves.

Search by content means "find the item that says Chen" when you don't know where it is. Neither structure can guess, so both have to check items one at a time from the start. That's why this row is a tie.

So the skill isn't picking a favorite. It's asking, "What will my program do most often?" Lots of looking things up by position? Use an array. Lots of inserting and removing in the middle? Use a linked list.

The trap: students often look for the "better" structure between the two. There isn't one — arrays win when you need instant access by position; linked lists win when you're constantly inserting and deleting in the middle. Naming both properties correctly is the actual skill being tested here, not picking a favorite.

14.3 Objects, Dictionaries & Searching Fast

Two more structures round out your toolkit: one for bundling related data and behavior together, one for looking things up by name instead of by position.

14.3.1 Objects

An object bundles data together with the procedures (called methods when they belong to an object) that act on that data. A car object might hold data like color and speed, plus methods like accelerate() and brake() that operate directly on that same data. This is the same idea as encapsulation, which you'll study in Chapter 15 — the data and the logic that's allowed to touch it travel together as one unit.

Breaking It Down: Objects & Methods

An object groups related information together under one name. Instead of separate variables like carColor, carSpeed, and carModel, you make one car object that holds all three. Each piece of information is called a property, and you reach it with a dot: car.color.

Objects can also hold methods, which are functions that belong to the object and work on its own data. A car's accelerate method changes the car's own speed. Inside a method, the word this means "this object," so this.speed is the speed of the car whose method was called.

Here's a car object with three properties and one method:

const car = {
  color: "red",
  model: "Civic",
  speed: 0,
  accelerate: function(amount) {
    this.speed = this.speed + amount;
  }
};

car.accelerate(10);
Logger.log(car.speed);   // 10

Objects match how we think about the real world. A student has a name, a grade, and a period, plus things you do with them, like updating their grade. Keeping the data and the actions together makes code easier to read and harder to mess up.

14.3.2 Dictionaries (Maps)

An array looks things up by numbered position. A Dictionary (or Map) looks things up by a meaningful key instead — a phonebook keyed by name instead of by an arbitrary row number is dramatically faster to search, because you go straight to the name instead of checking every entry in order.

Breaking It Down: Dictionaries: Look It Up by Name

A dictionary (also called a map) stores pairs: a key and its value. The key is how you find something, and the value is what you find. In a real dictionary, the word is the key and the definition is the value. In a phone's contact list, the name is the key and the phone number is the value.

The big advantage is speed. With an array of 1,000 contacts, finding "Maya" means checking names one by one until you hit her. With a dictionary, you ask for contacts["Maya"] and jump straight to her, just like going straight to the M section in a book.

In JavaScript and Apps Script, you can build a simple dictionary with an object, using names as the keys:

const grades = { "Amara": 92, "Ben": 85, "Chen": 78 };
Logger.log(grades["Ben"]);   // 85, found directly by key
grades["Deja"] = 88;          // add a new pair
grades["Ben"] = 90;           // update an existing value

One rule: keys must be unique. If two students are both named "Alex," saving the second one would overwrite the first. That's why real systems often use something guaranteed to be unique, like a student ID, as the key.

Binary Search

Binary search finds a target value in an already-sorted list by repeatedly checking the middle element and eliminating half the remaining possibilities — exactly like looking up a word in a printed dictionary by flipping to the middle, deciding which half your word is in, and repeating. It's dramatically faster than checking every item one by one, but it only works because the list is sorted first.

Breaking It Down: Binary Search, Step by Step

Play this game: "I'm thinking of a number from 1 to 100." A smart guesser doesn't say 1, 2, 3, 4... They say 50. If the answer is "higher," they've just ruled out half the numbers in one guess. Then they say 75, then 62, and so on. That strategy is binary search. "Binary" means two, because each step splits what's left into two halves.

Let's search this sorted list for 72: [2, 5, 8, 12, 16, 23, 38, 45, 56, 72, 91]. Step 1: check the middle (index 5), which is 23. Since 72 is bigger, throw away everything from 23 down. Step 2: the middle of what's left (index 8) is 56. Still too small, so throw away the left half again. Step 3: the middle of what's left (index 9) is 72. Found it in 3 checks instead of 10.

The savings get huge as lists grow. Checking one item at a time through 1,000 items could take 1,000 checks. Binary search needs about 10. For a million items, it needs about 20. Every check cuts the problem in half.

But there's a rule you can't break: the list must be sorted. Binary search throws away half the list based on whether the target is bigger or smaller than the middle. In an unsorted list, a number bigger than the middle could be hiding on either side, so throwing half away might throw away the answer.
