15.1 Procedures, Parameters & Return Values

Copy the same five lines of code into four different places in your script, and you've created four separate places that all have to be updated the moment the rule changes. A procedure fixes that by giving those five lines one name, called from wherever it's needed.

15.1.1 The Anatomy of a Procedure

Name

What you call it

Parameters

Named inputs it expects

Body

The actual steps it runs

Return Value

What it hands back

The Trap: Parameter vs. Argument

These two words get used interchangeably, but they're not the same thing. A parameter is the name written into the procedure's definition — function greet(name), where name is the parameter. An argument is the actual value passed in when you call it — greet("Jordan"), where "Jordan" is the argument.

Change one rule inside a well-named procedure once, and every place that calls it updates automatically — that's the entire payoff for the extra structure. A good procedure also follows the single-responsibility rule: it should do one nameable thing. A procedure trying to do five unrelated jobs is a sign it needs to be split.

15.1.2 Scope: What a Procedure Can See

Relying on a global variable inside a procedure — instead of passing it in as a parameter — makes that procedure unsafe to reuse elsewhere, because it silently depends on something existing outside itself that a future caller might not have set up.

Quick Check

In greet("Jordan"), which word is the argument? (Answer: "Jordan" — the parameter is the name written in the procedure's definition, the argument is the actual value passed when calling it.)

15.2 Combining Data & Procedures Into One Artifact

A working script and a finished tool can run the exact same logic and still feel completely different to use. The difference is integration: a menu, input validation, and clear feedback wrapped around the same working code.

15.2.1 Structuring a Real Tool

A well-structured script keeps data at the top, procedures grouped logically below it, and one clear entry point that orchestrates everything else — instead of logic scattered randomly wherever it was first written.

Worked Example: A Menu for Non-Technical Users

Add a custom menu to a spreadsheet so someone who has never opened the script editor can still run your tool with one click. That single addition is often what actually turns a working script into something a real teammate would use.

The trap: students often think "it works when I run it" means the tool is done. It means the logic is done. Validating input and handling failure cases gracefully is the part that separates a demo from something safe to hand to someone else.

Quick Check

What single addition lets a non-technical user run your tool without touching the script editor? (Answer: a custom menu.)
