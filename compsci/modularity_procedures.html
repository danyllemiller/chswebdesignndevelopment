15.1 Procedures, Parameters & Return Values

Copy the same five lines of code into four different places in your script, and you've created four separate places that all have to be updated the moment the rule changes. A procedure fixes that by giving those five lines one name, called from wherever it's needed.

Breaking It Down: Why Procedures Exist

A procedure (in JavaScript, a function) is a named set of steps you can use again and again. You've already been writing them: every function you made in Apps Script is a procedure. This chapter is about using them on purpose to keep your code organized.

Think about a school's rule for calculating a late penalty. If you copy that math into four different places, then the day the rule changes from 10% to 15%, you have to find and fix all four. Miss one, and your program now gives different answers in different places. That's a hard bug to spot.

Programmers have a saying: DRY, which stands for "Don't Repeat Yourself." Put the rule in one procedure, give it a clear name like latePenalty, and call that name everywhere you need it. Now there's only one place to change, and every part of your program stays in sync.

15.1.1 The Anatomy of a Procedure

Name

What you call it

Parameters

Named inputs it expects

Body

The actual steps it runs

Return Value

What it hands back

Breaking It Down: The Four Parts, in Real Code

Every procedure has the same four parts. The name is what you call it, so pick a name that says what it does, like average instead of doStuff. The parameters are the inputs it expects, listed inside the parentheses. They're like the blanks on a form.

The body is the steps inside the curly braces, where the work happens. The return value is the answer the procedure hands back with the word return. When the program reaches return, the procedure stops and sends that value back to whoever called it.

Here's a procedure with all four parts labeled:

function average(scores) {               // name + parameter
  let total = 0;                         // body starts
  for (let i = 0; i < scores.length; i++) {
    total = total + scores[i];
  }
  return total / scores.length;          // return value
}

let myAvg = average([80, 90, 100]);      // [80, 90, 100] is the argument
Logger.log(myAvg);                       // 90

Notice that average doesn't know or care whose scores it's averaging. You can call it with any list of numbers, from anywhere in your program. That flexibility is the whole reason parameters and return values exist.

The Trap: Parameter vs. Argument

These two words get used interchangeably, but they're not the same thing. A parameter is the name written into the procedure's definition — function greet(name), where name is the parameter. An argument is the actual value passed in when you call it — greet("Jordan"), where "Jordan" is the argument.

Change one rule inside a well-named procedure once, and every place that calls it updates automatically — that's the entire payoff for the extra structure. A good procedure also follows the single-responsibility rule: it should do one nameable thing. A procedure trying to do five unrelated jobs is a sign it needs to be split.

Breaking It Down: The Single-Responsibility Rule

The single-responsibility rule says each procedure should do one job. Here's a quick test: can you describe what it does in a short phrase without using the word "and"? "Calculates the average" passes. "Reads the sheet and calculates the average and emails the teacher and formats the cells" fails.

Why does this matter? Small, focused procedures are easier to test, because you only need to check one thing. They're easier to reuse, because "calculate an average" is useful in many places, but "read this exact sheet and email this exact teacher" is useful in only one. And when something breaks, the procedure's name usually tells you exactly where to look.

If a procedure is doing too much, split it. Make one procedure for each job, then write one short "main" procedure that calls them in order: readScores(), then average(), then sendReport(). Your code ends up reading almost like a to-do list.

15.1.2 Scope: What a Procedure Can See

Relying on a global variable inside a procedure — instead of passing it in as a parameter — makes that procedure unsafe to reuse elsewhere, because it silently depends on something existing outside itself that a future caller might not have set up.

Breaking It Down: Scope: Local vs. Global

Scope means where in your program a variable can be seen and used. A variable created inside a procedure is local: it only exists while that procedure runs, and nothing outside can see it. A variable created outside every procedure is global: every procedure in the file can see it and change it.

Globals seem convenient, but they cause sneaky problems. If a procedure quietly uses a global variable, it only works when that global exists and holds the right value. Copy the procedure into another project, or let some other code change the global, and it breaks, often without any error message.

Compare these two versions:

let taxRate = 0.08;   // global

// Risky: secretly depends on the global taxRate
function priceWithTax(price) {
  return price + price * taxRate;
}

// Safe: everything it needs comes in as a parameter
function priceWithTaxSafe(price, rate) {
  return price + price * rate;
}

The safe version gets everything it needs through its parameters, so it works anywhere, every time. A good rule: if a procedure needs a value, pass it in as a parameter instead of reaching outside for it.

Quick Check

In greet("Jordan"), which word is the argument? (Answer: "Jordan" — the parameter is the name written in the procedure's definition, the argument is the actual value passed when calling it.)

15.2 Combining Data & Procedures Into One Artifact

A working script and a finished tool can run the exact same logic and still feel completely different to use. The difference is integration: a menu, input validation, and clear feedback wrapped around the same working code.

15.2.1 Structuring a Real Tool

A well-structured script keeps data at the top, procedures grouped logically below it, and one clear entry point that orchestrates everything else — instead of logic scattered randomly wherever it was first written.

Breaking It Down: Structuring a Real Tool

Imagine opening a kitchen where pots, food, and spices are all mixed together in random drawers. You could cook, but it would be slow and frustrating. A well-structured script is like a well-organized kitchen: everything has a place, so anyone can find what they need.

A good layout has three parts, top to bottom. 1. Data and settings: things like sheet names and limits, kept at the top so they're easy to change. 2. Procedures: each one doing a single job, grouped by topic. 3. An entry point: one main procedure that runs the whole tool by calling the others in order.

The entry point is the "start here" of your tool. When a teammate opens your code, they can read that one procedure and understand the whole flow in a few lines, then dive into a specific procedure only when they need the details:

const SHEET_NAME = "Scores";        // 1. settings

function readScores() { /* ... */ }  // 2. procedures
function average(scores) { /* ... */ }
function writeReport(avg) { /* ... */ }

function runReport() {               // 3. entry point
  const scores = readScores();
  const avg = average(scores);
  writeReport(avg);
}
Worked Example: A Menu for Non-Technical Users

Add a custom menu to a spreadsheet so someone who has never opened the script editor can still run your tool with one click. That single addition is often what actually turns a working script into something a real teammate would use.

Breaking It Down: Building a Custom Menu

Most people who use your spreadsheet will never open the script editor, and they shouldn't have to. A custom menu adds your own menu to the top of the sheet, right next to Help, so anyone can run your tool with one click.

You build it inside an onOpen function. Remember from Chapter 10 that onOpen runs automatically every time the spreadsheet opens. Each addItem line takes two things: the words people will see in the menu, and the exact name of the procedure to run when they click it.

function onOpen() {
  SpreadsheetApp.getUi()
    .createMenu("Grade Tool")
    .addItem("Run Report", "runReport")
    .addItem("Clear Data", "clearData")
    .addToUi();
}

After you save, reload the spreadsheet tab and your menu appears. If clicking an item does nothing or shows an error, check that the procedure name in quotes matches your function's name exactly, including capital letters.

The trap: students often think "it works when I run it" means the tool is done. It means the logic is done. Validating input and handling failure cases gracefully is the part that separates a demo from something safe to hand to someone else.

Breaking It Down: Failing Gracefully

Failing gracefully means that when something goes wrong, your tool explains the problem in plain words instead of crashing or quietly producing wrong answers. A vending machine that says "Exact change only" is failing gracefully. One that just eats your money is not.

Before your tool uses any data, check it. Is the cell empty? Is it a number when it should be? Is it in a sensible range, like a score between 0 and 100? If a check fails, stop and show a helpful message. In a menu-driven tool, SpreadsheetApp.getUi().alert() pops up a message box:

function runReport() {
  const score = SpreadsheetApp.getActiveSheet().getRange("B4").getValue();
  if (score === "" || typeof score !== "number" || score < 0 || score > 100) {
    SpreadsheetApp.getUi().alert("Cell B4 must be a number between 0 and 100.");
    return;   // stop here instead of continuing with bad data
  }
  // ...the rest of the report only runs with good data
}

A good error message tells the person three things: what went wrong, where it happened, and how to fix it. "Error" is useless. "Cell B4 must be a number between 0 and 100" tells them exactly what to do.

15.3 Working Like a Real Dev Team

One person writing one script is one kind of programming. A team of developers sharing one codebase, building on each other's work, and reusing code nobody on the team wrote themselves is a different skill set entirely.

15.3.1 Recursion: A Procedure That Calls Itself

Recursion is a procedure that calls itself with a smaller version of the same problem, until it reaches a base case simple enough to answer directly. A factorial function calculating 5! calls itself to calculate 4!, which calls itself for 3!, and so on, until it hits the base case (1! = 1) and the answers combine back up the chain.

Breaking It Down: Recursion

Recursion is when a procedure solves a problem by calling itself on a smaller version of that same problem. It sounds like a loop that never ends, but it has a built-in stopping point called the base case.

Picture a line of people, and you want to know how many there are. You ask the person in front of you, "How many people are ahead of you, counting yourself?" They ask the person ahead of them, and so on. The very first person in line doesn't need to ask anyone. They just say "1." That's the base case. Then each answer passes back down the line, with each person adding 1, until the answer reaches you.

5! ("five factorial") means 5 × 4 × 3 × 2 × 1 = 120. Notice that 5! is just 5 × 4!, and 4! is 4 × 3!. Each problem contains a smaller copy of itself, which is exactly the shape recursion is built for:

function factorial(n) {
  if (n <= 1) {
    return 1;                  // base case: stop here
  }
  return n * factorial(n - 1); // recursive case: smaller problem
}

Logger.log(factorial(5));      // 120

Every recursive procedure needs two parts: a base case that stops the chain, and a recursive case that moves closer to the base case each time. Forget the base case, and the procedure keeps calling itself until the program crashes, which is recursion's version of an infinite loop.

15.3.2 Version Control & Code Review

A version control system like Git lets multiple developers work on the same codebase at once without overwriting each other's changes — it tracks exactly what changed, when, and by whom, and can combine everyone's edits together safely.

Breaking It Down: Version Control & Git

Have you ever saved files called "essay_final," "essay_final2," and "essay_REAL_final"? That's a homemade version-control system, and it gets messy fast. Version control is software that keeps a full history of every change to your code automatically, so you can see what changed, who changed it, and go back if something breaks.

Git is the most popular version-control system in the world. It was created in 2005 by Linus Torvalds, the creator of Linux. Each saved snapshot in Git is called a commit, and every commit gets a short message describing the change, like "Fix late penalty math." Websites like GitHub store Git projects online so teams can share them.

Teams use branches to work at the same time without getting in each other's way. A branch is your own copy of the project where you can build a feature. When the feature is ready, you merge it back into the main project, and Git combines your changes with everyone else's.

Sometimes two people change the exact same line in different ways. Git can't guess which one is right, so it flags a merge conflict and asks a human to decide. That's not an error. It's Git protecting your team from accidentally erasing each other's work.

Before new code gets merged in, a teammate typically performs a code review: reading through it looking for bugs, style problems, and anything confusing to a future reader. It catches mistakes before they reach real users, and it's also how a team keeps a shared, consistent style across code written by different people.

Breaking It Down: Code Review

A code review is when a teammate reads your code before it becomes part of the shared project. It's a lot like peer editing an essay: a second set of eyes catches things the writer is too close to see.

Reviewers look for a few main things. Are there bugs, like a loop that's off by one? Are the names clear, or would a newcomer wonder what x2 means? Is anything missing, like a check for empty input? And does it follow the team's style, so the whole project reads like one person wrote it?

Good review comments are specific and kind. "This is confusing" doesn't help. "Could you rename d to daysLate so it's clear what it stores?" does. Even professional programmers with decades of experience have their code reviewed, because everyone misses things.

Quick Check

What tool lets three developers edit the same file at once without wiping out each other's work? (Answer: a version control system like Git.)

15.3.3 APIs & Libraries

An API (Application Programming Interface) is a defined way for one piece of software to request something from another — a weather app doesn't recreate a national weather database, it sends a request in the exact format a weather service's API expects and gets data back. A library is similar in spirit: instead of writing your own date-formatting code from scratch, you import a well-tested package that already does it, saving time and avoiding bugs someone else already fixed.

Breaking It Down: APIs

An API (Application Programming Interface) is a set of rules for how one program can ask another program for something. Think of a restaurant. You don't walk into the kitchen and cook. You order from a menu, the server takes your order to the kitchen, and your food comes back. The menu is the API: it lists exactly what you can ask for and how to ask.

Apps use APIs constantly. A weather app sends a request to a weather service's API, like "current temperature for Carson City," and gets back data, not a whole web page. A "Sign in with Google" button uses Google's API. Even Apps Script commands like SpreadsheetApp.getActiveSheet() are part of Google's API for Sheets.

The big benefit is that you don't need to know how the other program works inside. You only need to know how to ask. The weather service could completely rebuild its system, and your app would keep working as long as the API's "menu" stays the same.

Breaking It Down: Libraries

A library is a collection of code that someone else wrote, tested, and shared so you can use it in your own project. Instead of writing your own code to handle dates, charts, or encryption from scratch, you include a library that already does it well.

Using libraries is like building with LEGO pieces instead of carving every brick yourself. It saves huge amounts of time, and popular libraries have been used and fixed by thousands of programmers. That usually makes them more reliable than something brand-new you wrote last night.

There are two things to check first. Is the library maintained, meaning someone still fixes its bugs and security problems? And what does its license allow? That's the trap described below, and Chapter 16 goes deeper into licenses.

The Trap: Skipping the License

Not every free library is free to use in every context. Before including one in a project — especially anything commercial — check its license. Some require crediting the author, some forbid commercial use entirely, and using code without checking is a real legal risk, not just bad etiquette.

15.3.4 Encapsulation & Vulnerabilities

Encapsulation means a piece of code keeps its internal data private and only lets other code interact with it through specific, defined methods — hiding the messy implementation details behind a clean, controlled interface, so nothing outside can reach in and corrupt its internal state directly.

Breaking It Down: Encapsulation

Encapsulation means hiding an object's inner data and only letting other code change it through approved methods. Think of an ATM. You can't reach into the machine and grab cash. You have to use the buttons, and the machine checks your PIN and your balance before giving you anything. The buttons are the approved methods, and the cash is the protected data.

Why protect data this way? Imagine a bank-account object where any code could directly set balance = -5000. One bug anywhere in the program could wreck the account. If the only way to change the balance is through deposit() and withdraw() methods, those methods can enforce the rules, like "you can't withdraw more than you have."

Here's the idea in code. The rules live inside the methods, so every change to the balance has to pass through them:

const account = {
  balance: 0,
  deposit: function(amount) {
    if (amount > 0) this.balance = this.balance + amount;
  },
  withdraw: function(amount) {
    if (amount > 0 && amount <= this.balance) {
      this.balance = this.balance - amount;
    }
  }
};

Encapsulation also makes code easier to change. As long as deposit() and withdraw() keep working the same way from the outside, you can completely rewrite how the inside works without breaking anyone else's code.

When code doesn't enforce boundaries like this carefully, it can create a vulnerability — a flaw an attacker can exploit, like a login form that doesn't properly check a password before granting access. Modifying existing code can also introduce an unintended implication: a change to one module unexpectedly breaking a completely different, seemingly unrelated part of the app that quietly depended on the old behavior.

Breaking It Down: Vulnerabilities

A vulnerability is a weak spot in software. An attacker can use it to do something they shouldn't. They might see private data, log in as someone else, or crash the system. Most weak spots are honest mistakes. Someone forgot a check, missed a rule, or never expected a certain input.

The login example above is a classic. Say a login form doesn't check the password the right way. An attacker might find a trick input that skips the check. Chapter 16 shows a famous example called SQL injection. In that attack, typing a special bit of text into a form tricks a database.

You already know many of the defenses. Check every input. Keep data protected so it can only change through approved methods. And never trust users to type what you expect. Real teams also run security reviews, and they fix weak spots fast once they find them.

Breaking It Down: Unintended Implications

An unintended implication is a side effect you didn't see coming: you change one part of your program, and a totally different part breaks. It happens because parts of a program quietly depend on each other in ways that aren't obvious.

Here's an example. You change a procedure so it returns a grade as a letter ("B") instead of a number (85), because your report looks nicer that way. But another procedure somewhere else was using that number to calculate class averages. Now the average calculation breaks, even though you never touched it.

This is why everything in this chapter works together. Small single-responsibility procedures, parameters instead of globals, encapsulation, and code review all make hidden dependencies easier to see. And it's why teams re-run all their tests after a change, not just the new ones. Chapter 16 gives this kind of bug its official name: a regression.
