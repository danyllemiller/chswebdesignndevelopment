Unit 3: Data & Analysis — Project

The Player Data Pipeline

You're the new data analyst at an indie game studio. Built in Google Sheets. 100 points.

Standards Addressed

Nevada Academic Content Standards for Computer Science & Integrated Technology: 9-12.DA.S.1 (translate between bit representations), 9-12.DA.S.2 (tradeoffs in how data is organized/stored), 9-12.DA.CVT.1 (interactive data visualizations), 9-12.DA.IM.1 (computational models of data relationships) — the same standards Chapter 5 (The Binary Translator, The Encoding Lab), Chapter 6 (The Organization Audit, The Storage Tradeoff Matrix), Chapter 7 (The Function Toolkit, The Chart Rebuild) and Chapter 8 (The Model Build, The Reality Check) build toward.

The Scenario

Byte Size Games, a small indie studio, just hired you as their first data analyst. Their game engine is live and generating real player data — but right now that data is either unreadable (raw binary/hex codes the engine logs to save space) or just sitting in a messy pile nobody can actually use. Your job over this project is to take that data through the same four stages every real data analyst does: decode it, organize it, visualize it, and use it to predict what happens next.

This isn't 4 separate assignments — it's one pipeline, one dataset, four stages. The player dataset you build in Stage 2 is the exact same dataset your Stage 3 dashboard charts and your Stage 4 prediction are built from. If your dashboard is about player scores, your prediction has to be about player scores too — not a random new topic. Each tab should feel like the next step in the same investigation, not a fresh start.

Objective

Build a real, 4-tab Google Sheets workbook that tells one continuous story about Byte Size Games' player data: decode it, store it well, show it clearly, and predict from it.

Deliverable: A Google Sheets workbook with 4 tabs (see below), built around one player dataset that carries through all four. Turn in a PDF export or a text file with your share link below.

The Four Stages (one tab each)

Each stage links to the chapter section that actually teaches how to do it — do that first if you haven't already. Work through them in order — each one hands off to the next.

  1. Stage 1 — Tab “Decode the Feed”: Byte Size Games' engine logs player events as raw binary/hex codes instead of plain text, to save bandwidth — an item-pickup code, a player-status code, a cosmetic color code like a hex value. Build a decoder key: a working reference table converting at least 8 real codes across binary, hexadecimal, decimal, and their real ASCII/Unicode character meaning, so the rest of the studio can actually read the engine's raw logs.
    How to: Ch 5.5, Doing This in Google Sheets »
  2. Stage 2 — Tab “Organize the Player Data”: Now that you can read the engine's codes, the studio hands you a real player dataset — scores, playtime, item pickups, whatever fits the codes you just decoded (self-generate realistic rows if you don't have a real export; at least 15 players/rows). Organize that same dataset two different ways — e.g. one big flat table vs. split into related tables — and write out the real tradeoffs of each: speed, size, ease of updating. The lead engineer is going to use your recommendation to decide how the real database gets built.
    How to: Ch 6.1, Organizing Data »
  3. Stage 3 — Tab “Studio Dashboard”: Using that same player dataset from Stage 2, build a dashboard with at least 2 real charts driven by live formulas (SUM, AVERAGE, COUNTIF, etc.) — not typed-in numbers — that the studio's producer could actually check every week to see how the game's doing.
    How to: Ch 7.1–7.2, Formulas & Data Visualisation »
  4. Stage 4 — Tab “Predict What's Next”: Based on a trend you can actually see in your Stage 3 dashboard, build a simple formula-based model that predicts a real future outcome for that same data (e.g. next week's active players, or whether a player with a given pattern is likely to keep playing). Then write a sentence checking whether the prediction actually held up against real or plausible follow-up data.
    How to: Ch 8.1, Building a Model »
