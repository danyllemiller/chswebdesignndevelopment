10.1 Conditionals

The same branching logic can be written three completely different ways — nested if statements, a switch, or a lookup table. All three run correctly. Only one is easy for a stranger to read six months from now.

Breaking It Down: What a Conditional Is

Every day you make decisions based on conditions. If it's raining, you grab a jacket. If your phone is under 20%, you plug it in. A conditional lets a program make the same kind of decision: it checks whether something is true, and then does one thing or another depending on the answer.

The most common conditional is the if / else statement. The program checks a condition, which is a question with a true-or-false answer, like "Is the score 90 or higher?" If the answer is true, it runs one block of code. If it's false, the else block runs instead. You can add more checks in between with else if. The program tests them from top to bottom and stops at the first one that's true.

Here's a grade calculator written with if / else if / else:

function letterGrade(score) {
  if (score >= 90) {
    return "A";
  } else if (score >= 80) {
    return "B";
  } else if (score >= 70) {
    return "C";
  } else {
    return "Needs work";
  }
}

Notice the order matters. A score of 95 is also greater than 80, but the program never gets that far. It stops at the first true condition. If the checks were in the opposite order, every score above 70 would get a C. When a conditional gives a weird answer, check the order of your conditions first.

Breaking It Down: Sequence, Selection, and Iteration

Almost every program is built from three basic control structures. Sequence means the steps run in order, one after another, top to bottom. Selection means the program chooses which code to run based on a condition: if this is true, do this; otherwise, do that. Iteration means repeating a block of code, which is what loops do (Section 10.2).

Conditionals, the if statements in this section, are how you write selection. For example, code that gives free shipping only if the order total is over $35 is using selection, because the program selects one path or the other depending on the total.

When you read any code, try labeling each part. Is this just steps in order (sequence)? Is it making a choice (selection)? Is it repeating (iteration)? Those three words show up a lot on tests, and almost any algorithm can be described using only those three ideas.

10.1.1 Justifying Your Choice

Choosing a control structure is a real skill, not a formality — you're weighing implementation effort, readability, and performance against each other, and the "best" answer depends on the situation.

Breaking It Down: Three Ways to Write the Same Decision

The same decision can be written in more than one way, and all of them can be correct. You've already seen if / else if / else. The second way is a switch statement. A switch compares one value against a list of exact matches, like checking which period a student is in. It's great when you're matching exact values, but it can't easily check ranges like "80 to 89."

The third way is a lookup table. Instead of writing a decision for each case, you store the answers in a list or table, and the program simply looks up the answer. It works like the menu board at a restaurant: you don't ask the cashier to decide your price, you look it up.

Here's the same "which room is my class in?" decision written as a switch and as a lookup table:

// Switch: compares one value against exact matches
switch (period) {
  case "A1": room = "Room 101"; break;
  case "A3": room = "Room 204"; break;
  default:   room = "Unknown period";
}

// Lookup table: the answers are data, not code
const rooms = { A1: "Room 101", A3: "Room 204" };
room = rooms[period] || "Unknown period";

Both give the same answers. The switch spells out each case as code. The lookup table keeps the data in one place, so adding a new period means adding one line of data, not writing a new piece of logic.

Breaking It Down: Choosing the Right One

If all three ways work, how do you choose? Programmers weigh three things. Implementation effort is how much work it takes to write and change. Readability is how quickly another person (or you, a month from now) can understand it and trust it. Performance is how fast it runs.

For most small programs, the speed difference between these three is so tiny you'd never notice it. That's why readability usually wins. A decision that's easy to read is easy to check, and code that's easy to check has fewer hidden bugs.

Here's a simple rule of thumb. Use if / else when you're checking ranges or a few different conditions. Use a switch when you're matching one value against many exact options. Use a lookup table when you have lots of cases that are really just data, like prices, room numbers, or grade cutoffs. Whatever you pick, be ready to explain why. That explanation is a big part of what the Decision Logic activity and the Unit 4 project ask you for.

The Trap: Nesting Four Levels Deep

A conditional nested four if statements deep might be completely correct and still be a readability failure — nobody can verify it at a glance, including you in a month. Flattening it with an early return or a lookup table often produces the exact same behavior in a form a human can actually check.

Worked Example: Flattening a Nested Conditional

Four nested if statements checking a grade range, one inside the next, can become a single lookup table mapping score ranges to letter grades — same logic, same output, radically easier to scan and trust.

10.2 Loops & Iteration

Write the same output line five times and count the repeated lines. Write one loop instead and watch the line count shrink while the capability grows — iteration is what lets a program scale past what a human would ever type by hand.

Breaking It Down: What a Loop Is

Imagine your teacher asks you to write "I will not talk in class" 100 times. You could write the sentence 100 times by hand, or you could find a way to write it once and repeat it. A loop is how a program repeats a set of instructions without you writing them over and over. Repeating steps like this is called iteration, and each single pass through the loop is one iteration.

Loops are everywhere in real software. Your music app loops through every song in a playlist. A gradebook loops through every student to calculate grades. A game loops dozens of times every second to redraw the screen. Without loops, programmers would have to write a separate line for every song, every student, and every frame.

Every loop needs a way to know when to stop. Otherwise it would repeat forever. As you'll see below, the two main kinds of loops, for and while, handle stopping in different ways.

10.2.1 The For Loop's Three Parts

A for loop has exactly three parts: initialize a counter, check a condition that keeps the loop running, and increment the counter each pass. A while loop skips the built-in counter and just keeps running as long as its condition stays true — the honest choice when you don't know in advance how many times you'll need to loop.

Breaking It Down: For Loops, Step by Step

A for loop is the best choice when you know how many times you want to repeat something. Its first line has three parts inside the parentheses, separated by semicolons. Here's a loop that counts from 0 to 4:

for (let i = 0; i < 5; i++) {
  Logger.log("Pass number " + i);
}

Part 1, Initialize (let i = 0): create a counter variable, usually called i, and give it a starting value. This happens only once, at the very beginning. Part 2, Condition (i < 5): before every pass, the loop asks, "Is this still true?" If yes, it runs the code inside. If no, the loop ends.

Part 3, Increment (i++): after every pass, add 1 to the counter. i++ is a short way of writing i = i + 1. So the loop goes: i is 0, run; i is 1, run; i is 2, run; i is 3, run; i is 4, run; i is 5, and now 5 < 5 is false, so it stops. That's exactly 5 passes.

Tracing a loop like this, one pass at a time on paper, is the single best way to understand what it will do. It's also exactly what the Iteration Build activity asks you to do before you run your code.

Breaking It Down: While Loops

A while loop is simpler: it just keeps repeating as long as its condition is true. There's no built-in counter. Use it when you don't know ahead of time how many times you'll need to repeat, like "keep asking for a password until the user types the right one" or "keep reading rows until you reach an empty one."

Because a while loop has no automatic increment, it's your job to make sure something inside the loop eventually makes the condition false. In the example below, each pass adds one row, so row eventually reaches a blank cell and the loop ends:

let row = 2;
while (sheet.getRange(row, 1).getValue() !== "") {
  Logger.log(sheet.getRange(row, 1).getValue());
  row++;   // without this line, the loop never ends
}

Here's the quick way to choose. If you can finish the sentence "repeat this ___ times," use a for loop. If the sentence is "repeat this until ___ happens," use a while loop.

The Classic Failures

Off-by-one error: a loop running one too many or one too few times, usually from confusing < with <=.

Infinite loop: a condition that never becomes false — almost always caused by forgetting the increment step.

Breaking It Down: Off-by-One Errors & Infinite Loops

An off-by-one error is when a loop runs one time too many or one time too few. It's the most common loop mistake in all of programming, even for experts. It usually comes from a single character: < versus <=. The loop i < 5 runs for 0, 1, 2, 3, 4 (5 times). The loop i <= 5 runs for 0, 1, 2, 3, 4, 5 (6 times). One tiny symbol, one extra pass.

Why does this matter? Suppose you have a list of 5 students. Their positions are numbered 0 through 4. A loop with <= would try to visit position 5, which doesn't exist, so you'd get a blank, an error, or wrong data. A loop that starts at 1 instead of 0 would skip the first student completely, and nobody might notice until that student's grade goes missing.

An infinite loop is a loop whose condition never becomes false, so it never stops. In Apps Script, the program will freeze until Google stops it after a few minutes. The usual cause is forgetting to change the counter, like leaving out i++ or row++. Without it, the counter stays the same forever, so the condition is always true.

The fix for both problems is the same habit: trace your loop on paper. Write down the counter's value at the start of each pass and check the condition each time. Do the first two passes and the last two passes, because that's where off-by-one errors hide.

The trap: students often think an off-by-one error is a sign something is deeply wrong with their logic. Usually it's one character — a stray = or a missing one — hiding in an otherwise correct loop. Trace it on paper one iteration at a time and it's almost always fast to find.

Quick Check

10.3 Events That Trigger Code

A script you have to manually launch every time is a script, not a tool. What turns it into something someone would actually use is an event — code that runs on its own, without you sitting there pressing "run."

Breaking It Down: What an Event Is

An event is something that happens that a program can notice and respond to. When you tap a button on your phone, that's an event. When a new text message arrives, that's an event. When your alarm goes off at 6:30 a.m., that's an event too, triggered by the time.

So far, your code only ran when you clicked Run. That's fine for testing, but real tools don't work that way. Nobody wants to open the code editor every time they need something to happen. Event-driven code waits quietly in the background and runs automatically when its event happens.

The connection between an event and the code it runs is called a trigger. Think of it like a motion-sensor light: the motion is the event, the sensor is the trigger, and the light turning on is your code running. You set up the trigger once, and after that it works on its own.

10.3.1 Event Types

The most common triggers: on open (fires when a file is opened), on edit (fires the moment a cell changes), on form submit (fires when someone submits a linked form), and time-driven (fires on a schedule you set, with nobody present at all).

Breaking It Down: The Four Trigger Types in Apps Script

On open runs your code every time someone opens the spreadsheet. To use it, name your function exactly onOpen, and Google runs it automatically. It's often used to add a custom menu to the top of the sheet, or to show a welcome message.

On edit runs your code every time someone changes a cell. Name your function exactly onEdit(e). The e holds information about the edit, like which cell changed (e.range) and what was typed in it. It's perfect for checking data the moment it's entered, which you'll do in the worked example below.

On form submit runs when someone submits a Google Form that's connected to your sheet. Imagine a club sign-up form: every time a student signs up, your code could instantly add them to the right team list. This trigger is set up in the editor's Triggers menu (the clock icon on the left side), not just by naming a function.

Time-driven triggers run on a schedule: every hour, every morning at 7 a.m., every Monday, and so on. They are also set up from the Triggers (clock) menu. A time-driven trigger could email a reminder about missing assignments every Friday afternoon, with nobody even logged in.

10.3.2 Why Event-Driven Code Needs More Care

Nobody is watching an event-driven script run — that's the whole point. Which means if it fails, it fails silently, with nobody there to notice. Validation and error handling matter more here, not less.

Breaking It Down: Validation & Error Handling

When you click Run yourself, you're right there to notice if something breaks. Event-driven code runs while nobody is watching. If it crashes or saves bad data, nobody finds out until much later, and by then the bad data may have spread to other formulas and reports.

Validation means checking that data makes sense before you use it. Is this cell supposed to hold a number? Then check that it really is a number. Is it supposed to be between 0 and 100? Check that too. Error handling is what your code does when the check fails: it shows a helpful message and refuses the bad data, instead of crashing or quietly saving garbage.

Here's an on-edit trigger that only accepts numbers in column B. If someone types a word instead, it clears the cell and pops up a message explaining why:

function onEdit(e) {
  if (e.range.getColumn() !== 2) return;   // only check column B
  const value = e.range.getValue();
  if (value === "") return;                // ignore erased cells
  if (typeof value !== "number") {
    e.range.setValue("");                  // reject the bad entry
    e.source.toast("Column B only accepts numbers. Please try again.");
  }
}

Notice the two early return lines. They make the code skip edits it doesn't care about, like changes in other columns or a cell that was just erased. Good event-driven code ignores what isn't its job and handles bad input politely, so the people using the sheet always know what went wrong and how to fix it.

Attach an on-edit trigger that checks whether a new value is a valid number before accepting it. Type in bad input on purpose — text where a number belongs — and watch the trigger catch it and reject it gracefully, instead of letting broken data flow silently into the rest of the sheet.

10.4 Lists & Systematic Testing

Thirty separate variables for thirty student names is unmanageable the moment you need to loop through them. And a program that "seems to work" hasn't actually been tested until you've deliberately tried to break it.

10.4.1 Lists (Arrays)

A list (or array) stores many related values under a single variable name instead of creating a separate variable for each one. Each value gets a position, called an index, usually starting at 0 — so the third item in a list of five names is at index 2, not index 3. Combined with a for loop, a list is what lets a program process a hundred items with the same few lines that would process one.

Breaking It Down: Lists, Arrays & Indexes

Imagine making a separate variable for every student in a class: student1, student2, student3, all the way to student30. Now imagine a new student joins. You'd have to change your code. A list, also called an array, solves this. It stores many related values together under one name, like one row of lockers with a single name painted above it.

Each value in a list sits in a numbered spot called its index. In most programming languages, including JavaScript, the index starts at 0, not 1. So the first item is at index 0, the second is at index 1, and so on. To get an item, write the list's name followed by the index in square brackets: students[2] means "the item at index 2," which is the third name.

Every list also knows how many items it holds. That number is its length. A list of 5 names has a length of 5, but its last index is 4, because counting started at 0. This is exactly why the off-by-one errors from 10.2 are so common with lists.

Lists and for loops are a perfect team. The loop's counter can be used as the index, so the loop visits every item, one after another. Because the loop uses students.length instead of a fixed number, the exact same code works for 5 students or 500:

const students = ["Amara", "Ben", "Chen", "Deja", "Eli"];
Logger.log(students[2]);        // Chen
Logger.log(students.length);    // 5

for (let i = 0; i < students.length; i++) {
  Logger.log(students[i]);
}
Worked Example: Looping Over a List

Instead of student1, student2, student3... a list holds all of them: students = ["Amara", "Ben", "Chen", "Deja", "Eli"]. A for loop then visits every index automatically, printing each name, without the code caring whether the list has 5 names or 5,000.

10.4.2 Systematic Testing

Confirming a function works on one normal input isn't enough. Systematic testing means deliberately checking a function against a set of test cases covering the situations most likely to break it: a normal, expected input; an empty input (nothing at all); and an invalid input (the wrong type, or an out-of-range value). Each of these individual checks is one test case — running all three together is what actually gives you confidence the function is solid, not just lucky on the one input you happened to try first.

Breaking It Down: Systematic Testing & Test Cases

When you test a program by trying it once and seeing that it works, you've only proven it works for that one input. Real users will type things you never expected: nothing at all, a word where a number belongs, a huge number, a negative number. Systematic testing means planning your tests on purpose to find those problems before your users do.

Each planned test is called a test case. A test case has three parts: the input you'll give the function, the expected result you should get, and the actual result you really got. If expected and actual match, the test passes. If they don't, you've found a bug, which is a good thing, because now you can fix it.

Here's a test plan for a function called averageScore that averages a list of scores. The empty test is the sneaky one: dividing by a list with 0 items gives NaN ("Not a Number") instead of a helpful answer.

Test case          Input              Expected result
1. Normal          [80, 90, 100]      90
2. Empty           []                 "No scores yet" (not NaN)
3. Invalid         ["eighty", 90]     "Scores must be numbers"

After you fix a bug, run all of your test cases again, not just the one that failed. A fix in one spot can accidentally break something that used to work. Re-running every test is how professionals make sure they moved forward, not sideways.
